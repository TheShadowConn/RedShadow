# Glossary {: .appendix }

| Term | Meaning |
|---|---|
| **Asset** | A system that can be tested, such as a web application, API or host. |
| **Assessor** | The person assigned to a retest round who records pass or fail. |
| **Audit chain** | The sequence of audit entries, each linked by a hash to the one before it. |
| **CVSS** | Common Vulnerability Scoring System. A vector string produces a score from 0.0 to 10.0. |
| **CWE** | Common Weakness Enumeration. A catalogue of weakness types, such as CWE-89 SQL injection. |
| **Draft** | A finding visible to the testing team only. |
| **Engagement** | One penetration test for one organisation. |
| **Evidence** | A file attached to a finding that supports it. |
| **False positive** | A reported issue that is not real. |
| **Finding access** | The setting that limits which findings a person sees inside an engagement: all, assigned or own. |
| **IDOR** | Insecure direct object reference: reaching another person's data by changing an identifier. |
| **MFA / two-step verification** | A second sign-in step using an authenticator app code. |
| **Pending verification** | A fix has been submitted and awaits a decision. |
| **Proof of concept** | The steps or payload that demonstrate a finding. |
| **RBAC** | Role-based access control. |
| **Retest round** | A batch of fixes sent to an assessor for verification. |
| **Risk accepted** | The client accepts a risk until an expiry date. |
| **Scope** | Where a role's permissions apply: which engagements and which findings. |
| **SLA** | The target time to fix a finding, set by severity. |
| **Verification** | A person confirming that a fix works and recording how. |
| **Scenario** | One use case or test inside an engagement, with its own name, description, pictures, dates and status. It has no owner and findings do not belong to it. |
| **Cost line** | One amount in one currency on an engagement, with a category and a date. Totals are per currency and never converted. |

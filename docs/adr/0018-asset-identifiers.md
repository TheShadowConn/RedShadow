# ADR-0018 Assets have many identifiers; identifiers are normalised and unique per organisation

Status: accepted (2026-11-18)

**Decision:** An asset owns any number of `AssetIdentifier` rows (kinds: ip, cidr, hostname, domain, url, mac, cloud_id, repo, package, other). Each identifier is normalised on write (`apps/organisations/identifiers.py`: IPv6 compressed, DNS names lower-cased and punycoded, default ports and trailing slashes and fragments removed from URLs, MAC addresses colon-separated, `.git` removed from repositories) and gets a `match_key`. A unique constraint on `(organisation, match_key)` means one identifier belongs to one asset of an organisation. Hostname and domain share the key family `dns`, so `web.acme.test` cannot be both on two assets. Exactly one identifier per asset is primary (partial unique index). `Asset.identifier` stays as a display copy of the primary identifier so older API clients and CSV matching keep working; the constraint `uniq_asset_org_type_identifier` was dropped because identifiers carry the uniqueness now. Assets are never matched by name.

**Conflicts:** Writing an identifier that another asset owns is refused with a message naming that asset (HTTP 400, `fields.identifiers`). Nothing is merged automatically. A Super Admin resolves a real duplicate with the explicit merge action (`POST /assets/{id}/merge`), which moves identifiers, engagement links and findings to the kept asset in one transaction. Every identifier write first locks the organisation row, so concurrent requests cannot both claim an identifier; the unique constraint is the second line of defence.

**Why:** One system is usually reachable by an IP address, a hostname and a URL. A single text field forced one asset per spelling, which produced duplicate assets and findings split between them. Normalising before comparing removes the case, slash and port variants that cause most duplicates. Per-organisation scope matches the existing rule that an asset belongs to one organisation (clients may reuse the same private IP).

**Consequences:** The data migration copies each existing `identifier` into a primary identifier (kind detected, `other` when it does not parse). Two legacy assets of one organisation that shared an identifier under different types keep only their old text for the second one; nothing is merged for them. Identifiers of archived assets stay reserved so an import cannot recreate them. Deleting an asset frees its identifiers.

## Phase 8 results (2026-11-13): CSV import and export

- **Import wizard** (new app `apps/imports`; migration `imports` 0001 and `findings` 0008): upload, match columns, check rows, import, done. Endpoints: `POST /imports` (multipart: engagement and file), `GET /imports` and `/imports/{id}`, `POST /imports/{id}/mapping` (also starts the check), `GET /imports/{id}/rows?status=` (comma list, paged), `POST /imports/{id}/commit {mode, duplicates}`, `POST /imports/{id}/cancel`, `GET /imports/{id}/errors.csv`, `GET /imports/template.csv`, `GET/DELETE /import-mappings` (own saved mappings). Needs `imports.create` to change anything and `imports.view` to read; scoped to engagements where the caller holds them (Remediation cannot import). Reading, checking and importing run in the worker on the `imports` queue; states: uploaded, parsing, parsed, validating, previewed, importing, completed, failed, cancelled.
- **Parsing**: UTF-8 (with or without BOM) then Windows-1252; comma, semicolon or tab; limits 10 MB, 50,000 rows, 60 columns, 100,000 characters a cell; refuses empty, binary, HTML and duplicate or blank headers; ragged and blank lines handled; nothing is ever evaluated.
- **Checking**: the same rules as creating a finding by hand (title, severity or CVSS vector, CWE list, asset in scope by name or identifier, lengths, ISO dates, http(s) references); severity words such as Informational, Moderate and Crit are understood and any other word can be mapped in the app; errors are stored per row and per field. Duplicates are found inside the file and against existing findings of the engagement (hash of title, asset, endpoint and CWE); a duplicate that points to a finding the viewer cannot see says so without naming it.
- **Import**: always drafts (`source=import`, `import_job` set, reported by the uploader); duplicates skipped by default or imported on request; "all or nothing" is refused while rows have errors and, like "valid rows only", runs in one transaction in chunks of 500 with refs reserved in blocks, so a failure leaves zero findings and the counter unchanged. One summary audit event per import (`import.committed` with counts, first and last ref, file hash) instead of one per finding, because writing 50,000 chained events inside one transaction would not finish in the task time limit. One import can run per engagement at a time; the daily `imports.cleanup` task closes jobs stuck for 30 minutes and deletes uploaded files of finished jobs after 30 days (rows and history stay).
- **Export**: `GET /findings/export.csv` (needs `exports.csv`; same filters as the list; only findings the caller can see, no drafts for Remediation; up to 50,000 rows else 409; formula characters neutralised; filters, row count and SHA-256 written to the audit log). Shared helper `apps/core/csvout.py` now also builds the audit export.
- **Screens**: Imports page (history, New import with engagement, file and template download), the wizard page per job (step bar, progress while the worker runs, column matching with suggestions and saved mappings, preview with counts and a problems filter, severity-word fixer, Change columns, import options, confirm dialog, summary with a problem report), Findings page Export CSV and Import CSV buttons, nav item Imports.
- Your decisions (all yes): drafts only; skip duplicates by default; 10 MB, 50,000 rows, 60 columns; files kept 30 days; Remediation can export (scoped) but not import; done in one go.
- Checks: 672 backend tests pass (96 new in `tests/test_imports.py` and `tests/test_findings_export.py`, including a real 50,000-row import and a forced mid-import failure that rolls back), `make lint` clean, `tsc --noEmit` clean, production build ok, `make smoke` 34/34, `make drill` passed, real stack rebuilt and its worker consumes the `imports` queue.
- Browser-verified on a throwaway `rs_qa` stack (removed with its volumes, 0 left): Pentester uploaded an 8-row CSV (header names guessed correctly), matched columns, checked rows (2 valid, 4 errors, 2 duplicates with a link to the existing finding), fixed a severity word in the app, imported 3 drafts through the real worker (3 imported, 2 skipped, 3 left out, summary and checksum shown), the drafts appear in the findings list with asset, date and mapped severity, the findings export downloaded and was logged with 4 rows and a hash, the phone layout of the history. ## Phase 5A results (2026-11-13): state machine and remediation timeline (backend)

- State machine: `apps/findings/lifecycle.py` holds the one table of moves (blueprint section 5.4, plus the decisions below); `services.transition` is the only executor. One transaction per move: row lock, version check (409), permission check (403, audited), required note or input (400), status change, note, timeline entry and audit event commit together. `POST /findings/{id}/transition` takes `{to, version, note?, risk_accepted_until?, duplicate_of?}`. `publish`, `false-positive` and `duplicate` endpoints stay and call the machine.
- New data (migrations 0005, 0006): `RemediationActivity` timeline (append-only by database trigger; `GET/POST /findings/{id}/activity`, POST takes `fix_deployed`, `mitigated`, `comment` with optional evidence ids), finding fields `due_date`, `resolved_at`, `verified_at`, `verified_by`, `closed_at`, `risk_accepted_until`, `risk_acceptance_reason`, note kinds `verification` and `retest` (written only by transitions, never by hand).
